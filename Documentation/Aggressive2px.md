# Aggressive 2-pixel/cycle FoM experiment

This branch keeps the verified 1-pixel/cycle implementation in `RTL/top.v` untouched and contains two experimental 2px architectures:

1. `top_2px`: fully parallel exact 18-product MAC.
2. `top_2px_mp4`: **FoM-focused candidate using only 4 shared DSP multipliers clocked at 120 MHz**.

## Verified 2px front end

- `controller_2px.v`: issues two adjacent image addresses per cycle: 0/1, 2/3, ..., 30/31.
- `image_memory_2px.v`: two synchronous read ports.
- `line_buffer_2px.v`: advances both line-delay chains twice per clock.
- `window_generator_2px.v`: constructs two adjacent KxK windows per cycle.

For the default 32x32, K=3 case, the stream contains 512 two-pixel input blocks and 900 output pixels. The target steady-state throughput is **2 output pixels/system-cycle**.

## Arithmetic correctness

A general programmable 3x3 kernel needs 9 products per output. Two adjacent outputs therefore require 18 exact products. The six overlapping input pixels cannot reuse their old products because the one-pixel window shift changes the kernel coefficient applied to each shared pixel.

The original `mac_pair.v` implements the exact 18 products in parallel.

## FoM optimization: `top_2px_mp4`

The optimized candidate keeps the 2px streaming front end but replaces the 18 parallel multipliers with a **4-DSP time-multiplexed MAC**:

- system clock: 20 MHz
- internal MAC clock: 120 MHz generated by `clock_5x.v`
- DSP multiplier lanes: 4
- products per fast cycle: 4
- fast cycles per output pair: 5
- exact products per pair: 18
- system-level throughput target: 2 output pixels/cycle

The product schedule is:

```text
slot 0 -> left[0..3]
slot 1 -> left[4..7]
slot 2 -> left[8] + right[0..2]
slot 3 -> right[3..6]
slot 4 -> right[7..8]
```

The MAC explicitly sign-extends the unsigned pixel and signed kernel operands before multiplication. This is required because Verilog multiplication expression sizing can otherwise truncate the product before assignment to a wider destination.

### Fast/system CDC result path

The MP4 MAC uses a small **4-entry asynchronous result FIFO** between the 120 MHz MAC domain and the 20 MHz system/output domain. The FIFO uses Gray-coded read/write pointers with two-flop pointer synchronizers. This is required because a simple 1-bit completion toggle plus a 2-slot mailbox can overwrite an earlier result before the system clock domain consumes it.

The FIFO stores both 20-bit output accumulators as one result-pair entry. Under continuous operation, the consumer drains one pair per system cycle, preserving the required **2 output pixels/cycle** interface rate.

## Simulation: optimized candidate

From the repository root, open Vivado Tcl and run:

```tcl
source Scripts/run_simulation_2px_mp4.tcl
```

The script writes the generated output into the repository-level:

`sim/rtl_output_2px_mp4.mem`

Expected console result:

```text
TB_TOP_2PX_MP4: captured 900 outputs from 450 pairs (expected 900 outputs)
TB_TOP_2PX_MP4: OUTPUT COUNT MATCHES EXPECTATION
```

Then, in normal VS Code/PowerShell with `.venv` active:

```powershell
python Python/verify.py --image Images/input_32x32.mem --kernel Images/kernels/edge_3x3.mem --rtl-output sim/rtl_output_2px_mp4.mem --img-size 32 32 --k 3 --acc-width 20
```

Expected:

```text
Compared 900 output values.
RESULT: PASS - RTL output matches the golden model exactly.
```

### ReLU test

The optimized testbench accepts the `RELU=1` plusarg. After running the simulation with ReLU enabled, verify with:

```powershell
python Python/verify.py --image Images/input_32x32.mem --kernel Images/kernels/edge_3x3.mem --rtl-output sim/rtl_output_2px_mp4.mem --img-size 32 32 --k 3 --acc-width 20 --relu
```

## FoM

For throughput `T`, total power `P`, LUT `L`, DSP `D`, and BRAM `B`:

```text
FoM = T / (P * (L + 50*D + 100*B))
```

The target is `T = 2` output pixels/cycle.

Preserved baseline:

```text
T    = 1 px/cycle
LUT  = 842
FF   = 758
DSP  = 0
BRAM = 0.5
P    = 0.149 W
FoM  = 7.52e-3
```

For reference, beating the baseline at T=2 requires:

```text
P * (L + 50*D + 100*B) < 265.816
```

With D=4, this becomes:

```text
P * (L + 200 + 100*B) < 265.816
```

So the optimized branch has a concrete implementation target rather than merely a throughput target.
